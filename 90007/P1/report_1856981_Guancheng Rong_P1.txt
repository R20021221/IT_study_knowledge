Traceroute probes the network path hop-by-hop by sending serialized UDP or ICMP messages with 
incrementing TTLs to the destination host. It uses the ICMP timeout messages returned by the router when the 
TTL expires to record the IP address and round-trip delay of each hop. 
Therefore, we could use Wireshark to return ICMP protocol to obtain every hop’s IP address. We also can 
get IP addresses directly from terminal. 
My Wireshark capture filter is icmp or (udp and portrange 33434-33534). The first part, ICMP, captures 
all ICMP protocol packets—this corresponds to the ICMP Time Exceeded message returned by the router 
during traceroute and the ICMP Destination Unreachable message returned by the final destination.  Part 2, UDP 
and portrange 33434-33534. This port range covers 100 ports after the default starting port 33434 of traceroute, 
which is sufficient to capture all UDP probe packets in a normal traceroute session.  They are sent to the target 
host in UDP protocol, with the destination port increasing hop by hop starting from 33434.

From Fig 2.2.2(a), we could easily find the R2 = 0.385 and r = -0.620. The linear fit: y = -0.01360*x + 
41.14. When the distance is increasing, the hop count is falling. 
We could know the relationship between hop count and Geographic Distance is negative correlation. 
There are two major reasons: 
1. Long-distance routes often utilize large backbone networks. These backbone networks have high routing 
optimization and fewer hops. Short-distance routes, on the other hand, may involve peering through multiple 
smaller ISPs, increasing the hop count with each peering. For example, in our diagram, the distance between 
Cuenca and Ecuador is only ~13,500km, but the hop count is as high as 26, indicating that the route to South 
America passes through many intermediate networks. 
2. We could know that Hop count reflects network topological distance, not geographical distance. Two 
geographically distant nodes directly connected by the same submarine fibre optic cable may have a low hop 
count; conversely, geographically close nodes that traverse multiple Autonomous Systems (AS) will have a high 
hop count. [3, p.396] 
From Fig 2.2.2(b), when we divided the chart by continents, we could find that the six servers in Europe 
showed a strong negative correlation (r = -0.616), while the three servers in North America showed almost no 
correlation (r = -0.170). This indicates that the strength of the correlation depends on whether the routing paths 
share a similar backbone network structure.

Fig. 3.2.13 clearly shows that the actual physical distance and jitter exhibit a negative correlation; that is, as

According to Fig 3.2.14, we can clearly see that the coefficient of the fitting function in the chart is 
approximately 0. At the same time, we can also see directly from the chart that the fitted line is approximately a 
horizontal line. This reflects that in most cases, the average RTT does not change with geographical location. 
This suggests that it may be more related to the parameters of the server itself and the signal quality.  
All measurements were conducted over a shared Wi-Fi network in a student apartment building, where the 
wireless access point serves many concurrent users across the entire building. The typical download speed 
observed on this network is approximately 80 Mbps. During evening peak hours, when residents are streaming 
video, gaming, and downloading files simultaneously, noticeable increases in latency and network instability 
were observed. 
This shared wireless environment has two significant implications for the results. First, the Wi -Fi access 
point introduces additional queuing delay underload, which is added to every ping measurement regardless of 
the destination. This constant local overhead raises the baseline RTT for all hosts and diminishes the relative 
contribution of geographic propagation delay, helping to explain why RTT shows virtuall y no correlation with 
distance (r = 0.002). Second, fluctuations in local network load introduce variability that dominates the jitter 
measurements. For example, speedtest.masnet.ec recorded a jitter of 42.076ms in Run 1 and 41.764ms in Run 2, 
but only 5.327ms in Run 3 — an eightfold difference across three runs to the same host over the same path. The 
only variable that changed between runs was the local network congestion at the time of measurement. 
Similarly, iperf.he.net recorded an RTT spike of 475.908ms in Run 1 (compared to a typical range of 280–
350ms in Runs 2 and 3), which is consistent with a momentary burst of congestion at the local access point.  
However, local network conditions alone do not account for all observed variation.  
dal.speedtest.clouvider.net achieved both the lowest RTT (193.039ms) and the lowest jitter (2.155ms) among all

Firstly, bandwidth-delay product (BDP) is defined as the product of a link's bandwidth and the round-trip 
delay time [5]. It represents the maximum amount of data that can be in transit on the network at any given 
moment. A higher BDP indicates that the network path has a larger capacity for in -flight data, which is 
important for TCP performance — the TCP send window must be at least as large as the BDP to fully utilise the 
available bandwidth [5]. In summary, the BDP determines the minimum size required for a TCP send window. 
If the send window is smaller than the BDP, the sender cannot continue sending data while waiting for the 
ACK, resulting in link utilization falling below 100% and actual throughput being far lower than the available 
link bandwidth.

The bandwidth-delay product (BDP) for each host was calculated using the formula BDP = Mean 
Bandwidth ×  Mean RTT, where the mean bandwidth values were obtained from the iperf measurements in 
Section 4.1 and the mean RTT values from the ping measurements in Section 3.2. 
The highest BDP belongs to spd-desrv.hostkey.com (3,347 KB), despite it not having the highest 
bandwidth. This is because BDP is the product of both bandwidth and delay: spd -desrv achieves a high 
bandwidth of 85.1 Mbps combined with a relatively high RTT of 322.2ms, resulting in a large "pipe" that can 
hold a significant amount of in-flight data. In contrast, dal.speedtest.clouvider.net has the highest measured 
bandwidth (98.0 Mbps) but the lowest RTT (193.0ms), so its BDP ranks only fifth at 2,309 KB. This  illustrates 
an important characteristic of BDP: a low BDP does not necessarily indicate poor network performance. 
dal.clouvider delivers the best throughput and the most stable connection among all 10 hosts, yet its short round -
trip time means fewer bytes need to be in flight at any given moment to keep the pipeline full. From a TCP 
performance perspective, a lower BDP is actually easier to manage, as it requires a smaller TCP send window to 
achieve full link utilisation [5]. 
The two lowest-ranked hosts, porto.speedtest.net.zon.pt (535 KB) and speedtest.masnet.ec (615 KB), both 
have BDP values well below the average of 1,918 KB. Their low rankings are driven primarily by their limited 
bandwidth (13.8 and 14.2 Mbps respectively), rather than by their RTT values. As discussed in Section 4.2, 
Porto’s bandwidth is constrained by what appears to be ISP-level or server-side rate limiting at approximately

13.8 Mbps, while Ecuador server’s capacity is similarly limited. No matter how high the RTT, the BDP cannot 
grow when the bandwidth is capped at such a low level. 
The measurements were conducted over a shared Wi-Fi network with an observed download speed of 
approximately 80 Mbps. This means that for hosts where the measured iperf throughput approaches or exceeds 
80 Mbps — such as dal.speedtest.clouvider.net (98.0 Mbps) and spd-desrv.hostkey.com (85.1 Mbps) — the 
local wireless link may itself have become the bottleneck. In these cases, the true end -to-end BDP of the 
network path could be higher than what was measured, as the local access point limits the achievable 
throughput. For hosts with lower bandwidth measurements, such as Porto and Ecuador, the bottleneck lies at the 
remote end rather than the local network, and the measured BDP is likely representative of the actual path 
capacity. 
 
Ans 4.4  
Challenge 1: iperf.he.net refused default (sender) mode connections. 
When running the standard iperf3 command (iperf3 -c iperf.he.net) against Host 10 (iperf.he.net), the 
server refused the connection in its default mode, where the client sends data to the server. This is not a network 
connectivity issue but rather a server-side policy restriction — the iperf3 server at iperf.he.net is configured to 
only accept reverse-mode connections. To resolve this, the “-R” flag was used (iperf3 -c iperf.he.net -R)[6], 
which reverses the data flow direction so that the server sends data to the client instead. This resulted in 
successful bandwidth measurements across all three runs. It is worth noting that the -R flag is an iperf3-specific 
feature and is not available in iperf2, which is why iperf3 was used for this host while iperf2 was used for the 
remaining nine hosts. 
 
Challenge 2: Significant jitter spike on the Ecuador server's path during the nighttime slot.  
During the Section 4.2 night measurement (AEST 23:08), the traceroute to the Ecuador server revealed a 
severe jitter spike at hop 24 (voip.masnet.ec, 170.83.216.5), with RTT values of 524.668ms, 327.077ms, and 
388.391ms across the three probes. In comparison, the morning tracer oute for the same hop recorded a stable 
327/327/328ms. This hop is labelled "VoIP" in its hostname, suggesting it functions as a VoIP gateway within 
the Ecuador ISP's network. The instability at this node during the nighttime slot (co rresponding to 
approximately 08:00 local time in Ecuador, the start of business hours) is consistent with increased traffic load 
from voice and data services. This jitter spike also coincided with the final -hop RTT increasing from ~326ms to 
413ms, and the iperf bandwidth dropping to 20.8 Mbps (the second-lowest value across the four time slots). 
However, the TCP connection did not collapse entirely, indicating that TCP's congestion control and windowing 
mechanisms were able to absorb the jitter to some extent, maintaining a usable level of throughput despite the 
unstable intermediate node.
